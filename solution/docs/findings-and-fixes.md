# Findings and fixes

This document records what we found — in the supplied data and in our own
pipeline — and what we did about it. It is the engineering evidence behind the
End Report: the kit's real behaviour, the disagreements between the catalog and
the corpus, the defects we found in our code during self-review, and the limits
we state rather than hide.

Everything here is reproducible from this solution with the practice kit.

---

## 1. What the supplied kit contains (verified from the raw logs)

The corpus is generated by the organiser simulator, so the config timeline and
the ground truth are written by the same code that places the faults. That makes
the data internally consistent and findable by ordinary analysis, which is the
point.

| Quantity | Value |
|---|---:|
| Sessions | 80,252 |
| Sessions, `v3_agent` / `v2_flow` | 68,492 / 11,760 |
| `v3` share, acme-bank / northwind-retail | 0.7205 / 0.9308 |
| Days | 56 |
| Config changes | 16 |
| Human rubric labels | 96 |

### The three real faults

**F1 — knowledge-base gap, acme-bank, `premium_card_info`.** A new intent is
injected on day 35 and recovers after the fault window. In-window resolution is
**n=230, 0.3087**; after the window it is **n=301, 0.7907**. Its sessions are
assigned to a *random* acme v3 agent, so this is an intent-level finding, not an
agent-level one. Reporting a lifetime average, or blaming an agent, would both be
wrong.

**F2 — silent tool contract break, northwind-retail, `order_status` /
`get_order_status`.** The tool returns HTTP 200 with `outcome="ok"` but
`result_field_count=0`. Resolution falls 0.8522 → 0.7755, handoffs rise
0.0919 → 0.1698, while the *declared* tool-error rate stays flat (0.0145 →
0.0156). This is the fault that alerting cannot see, which is why it matters.

**F3 — prompt regression, acme-bank, `acme_main_v3`.** Median turns 4 → 6 and
mean turns 4.51 → 7.02 while resolution stays flat (0.7893 → 0.8031) and cost per
session roughly doubles. Peer agents `acme_cards_v3` and `acme_lending_v3` stay
flat in the same window, which is the control that proves the cause is the agent,
not the period.

### The three lookalikes

- **Traffic mix** (acme, `branch_locator` weight ×5): aggregate containment moves
  while every intent's own rate is flat.
- **Flash load** (northwind): volume ×4 and latency up, then it self-corrects;
  outcomes are flat.
- **Judge-version boundary** (both tenants): the rubric changes, so judged quality
  drops without the agent changing. v1 mean 3.872, v2 mean 3.256.

### How the faults are anchored

The sealed generator varies **days, lengths and rates only**; it does not move
tenants, cohorts or cause classes. We therefore use a config-anchored,
statistical detector rather than any practice literal, which is what lets the same
code pass renamed-label, moved-fault and extra-tenant corpora. A judge boundary
can fall inside a fault window, so quality is always segmented by
`judge_version`.

## 2. Catalog vs corpus: three disagreements (found, then handled by measuring)

We treat the mounted corpus as the truth for measurement and never edit the
organiser-owned kit files.

1. **Calibration set size.** The catalog says "100 human-scored sessions";
   `manifest.json` and `labels/rubric_scores.jsonl` are **96**. The published
   calibration uses n=96.
2. **The `v2_flow` coverage claim is half wrong.** The catalog declares that
   `v2_flow` lacks `kb_lookup` and cost, giving `cost_per_session` and
   `kb_fallthrough_rate` a declared coverage of 0.72/0.93. In the corpus, all
   11,760 v2 sessions carry `cost_usd` and v2 emits 10,997 `kb_lookup` and 612
   `guardrail` steps. Only `tool_call` is genuinely absent (0 rows). So the tool
   metrics really do cover 0.72/0.93, and the KB/cost claim is stale. Each
   affected metric carries a structured `coverage.observed_vs_declared` note
   rather than trusting the prose.
3. **One data repair.** A line in `labels/outcome_labels.jsonl` had a pasted
   filesystem path inside a session id. It was restored to `s_nort_042184`, which
   the corpus confirms. The pipeline never reads this file, so no number moved.

## 3. Defects we found in our own pipeline, and fixed

We audited the pipeline against a fixed edge-case list. The defects below were
real; each fix is in the shipped code.

| Defect | Effect | Fix |
|---|---|---|
| A loop variable shadowed the all-session list | Judged quality, the failover-proxy count and the cardinality count silently covered one tenant only | Renamed the loop variable; the counts cover both tenants |
| Missing cost was labelled as infinite unit cost | An intent with a telemetry gap read as the worst case | Separated `unbounded` (zero resolutions) from `cost_unavailable` (resolves, but unpriced) |
| Empty tool success treated a missing field as zero | A valid response with no result-field key would be flagged as a failure | Only an explicit `result_field_count == 0` counts as empty; a missing key is unknown |
| The mix-adjusted month comparison mixed two intent scopes | The change beyond mix partly measured a change in which intents were included | Both ends now sit on the common-intent scope; a cohort born in month 2 is named |
| The traffic-mix dismissal skipped small cohorts silently | A genuine small-cohort drop could be waved away as mix | An absolute guard (`MIX_SMALL_TOL`) covers small cohorts and quiet ones are named in evidence |
| The window-length cap was `D//2` | A long-running fault could not be enclosed by the scan | Raised to `D`, bounded by the 7-day outside requirement |
| A06 went silent when calibration was unavailable | An ask vanished instead of being answered | It files a gap when fewer than 10 human labels join |
| `plan.breakdowns` could disagree with the produced breakdown | A metric's stated plan did not match its output | The produced breakdown is the single source for the plan |
| Regenerating the report wiped recorded approvals | A human verdict was lost on the next run | Approvals are carried forward by `(id, diagnosis_id, target)` and the run notes `PRESERVED` |
| Step-grain facts were missed when a session field was absent | By-design handoffs and milestones could be undercounted | Added step-grain fallbacks |
| Writes were not fully atomic | A crash mid-write could corrupt the report | One `write_json_atomic` helper (unique temp file, `fsync`, `os.replace`) for report, golden set and screen |
| A corrupt report dropped the connection | The screen failed opaquely | `GET /report.json` returns `500 report_invalid`; concurrent decisions are serialized by a lock |
| A non-JSON replay response crashed the run | A flaky endpoint could abort the pipeline | It is treated as `unavailable`; the report stays valid |
| A pasted path inside a label session id | A visibly broken label file | Repaired (file is unread; no score change) |

The same audit produced the full defect list in the End Report (§17.4).

## 4. What we refuse to answer, on purpose

Refusing is part of the method, not a gap in it.

- **A11 (failover rate) is `NOT_MEASURABLE`.** No failover mechanism exists, so no
  event is emitted. We name the required event — `failover` at step grain, fields
  `from_target, to_target, reason, recovered`, owner `conversation-runtime` — and
  reject the tempting proxy: `llm_call.retry_count > 0` is a quality retry, not a
  switch to an alternate target.
- **The A02 `customer_ref` breakdown is refused** against the catalog's fixed
  budget of 200, since the field has ~80,252 distinct values.
- **A09 (why users abandon) is a `REQUIRES_NEW_JUDGE` gap.** Abandonment is
  measured; the *reason* needs a versioned judge that does not exist.
- **A06 files a gap** rather than publishing a quality reading with no calibration
  behind it.

## 5. Statistical caveats we state rather than hide

These are properties of the method, and they are the answer to "how much should I
trust this".

- **Independence.** The Welch z treats sessions as independent draws, but they
  cluster by day, agent, prompt version and KB version, so the effective sample is
  smaller than `n` and the z is optimistic. The high floors (4–6) are an informal
  offset, not a cluster-robust test.
- **Multiple comparisons.** The window scan maximises over ~1,500 candidate
  windows per series across ~50 cohorts, so an unadjusted z=4 is not a
  1-in-30k event. The floors plus absolute-lift requirements are the guard.
- **Winner's curse.** The window is chosen because it contrasts most, and the
  effect is then estimated on those same days, so effect sizes are inflated.
- **Degenerate baselines.** "0.0% outside (z=21)" is a zero-variance baseline; the
  z is driven by the degenerate outside, not by precision.
- **Two z estimators.** Detection uses an unpooled (Welch) SE; the mix-flatness
  guard uses a pooled two-proportion SE, so "z ≥ 4" is not the same test in both
  places.
- **Estimand.** Efficiency detects on mean turns but also reports median turns;
  heavy tails make them disagree, so both are printed.
- **Confidence is a prior.** `diagnoses[].confidence` is a hand-set author value,
  not a calibrated posterior.
- **Severity is effect size only**, with no sample-size term.
- **Efficiency conditions on resolved sessions**, so it is selection-biased if a
  fault changes which conversations resolve.
- **No cross-tenant control by design** — peers and siblings are same-tenant, so a
  global provider fault is invisible to the detectors. This avoids tenant
  confounds at the cost of global-fault blindness.
- **Controls can move with the fault.** If the whole KB degrades or every sibling
  moves, the control defeats itself and the fault is under-reported.
- **Right-censoring.** Conversations still open at export are not modelled.

## 6. Limits at scale

| Limit | What happens |
|---|---|
| In-memory session map | ~80k sessions / ~900k steps is comfortable; tens of millions would need an on-disk grain and a streaming window scan. |
| Single-file decision store | Atomic replace suits one operator; concurrent approvers would need a database. |
| Statistical detector floors | A sealed corpus whose empty-success rate sits under the lift/z floors will not fire — that is a miss, recorded as a miss, not a false clean bill of health. |
| Cost at session grain | If cost moved onto steps, a roll-up would be needed. |

## 7. Still to verify on a sealed or other corpus

- Autocorrelation magnitude; day-of-week / seasonality effects.
- Coverage computed globally versus per tenant (a tenant-specific emission hole).
- Cost missingness (are expensive sessions preferentially unpriced?).
- Right-censoring at export.
- The golden-set fingerprint keys on corpus shape, not content.
- `jsonschema` is absent here, so validation uses the built-in subset checker; an
  environment with it installed is the stricter authority.
