# Solution overview

**Nexus Loop** is a deterministic, standard-library-only Python pipeline
(`nexus_loop/` + `run.py`) that reads an already-deployed AI support agent's logs
and produces a schema-valid `loop-report.json`, plus a small operator decision
screen. It is the submission; the testbed in `tools/testbed/` is how we check
that it generalises.

This document is the technical overview: what the system does, how it is built,
and what it produces. For the honesty note see `docs/submission-note.md`; for the
issues we found and fixed see `docs/findings-and-fixes.md`.

---

## 1. Problem and objective

A deployed agent writes a lot of data — conversations, tool calls, retrieval
lookups, model calls, end states, and a timeline of configuration changes. The
task is to turn that into a closed loop rather than a manual investigation. The
system covers four stages:

1. **Detect** genuine problems and the traffic slice they affect.
2. **Diagnose** the cause and, where one exists, the configuration change behind it.
3. **Prescribe** one concrete fix and state the risk of shipping it.
4. **Verify** the fix on a replay service.

Two rules govern everything: never ask a language model for a fact the logs
already record, and never change the yardstick (metric definitions, judge
versions, the reviewed set of good conversations) to make a result look better.

An operator reading the final screen should be able to answer six questions: what
broke, who was affected, why it happened, who should act, what happens if nobody
acts, and whether the proposed fix can be trusted.

## 2. What we deliver

| # | Deliverable | Where |
|---|---|---|
| 1 | `loop-report.json` — generated by the system, valid against the organiser schema, produced unedited from the run | `out/loop-report.json` |
| 2 | The operator decision screen — a finding, its evidence, and a working approve/reject control that writes the verdict back | `python3 -m nexus_loop.app` |
| 3 | This documentation set: overview, findings and fixes, and the honesty note | `docs/` |

The report is produced by `run.py`; no hand-edited or reference report is read or
copied.

## 3. How to run

```bash
# 1. (optional) start the replay service, in another shell
python3 tools/nexus-loop-kit/replay/serve.py --kit kit --port 8719

# 2. cold run (one command, unattended)
python3 run.py --kit kit --team <name> --out out/loop-report.json

# 3. score against the practice key
python3 tools/nexus-loop-kit/score.py \
  --report out/loop-report.json \
  --ground-truth kit/ground_truth/ground_truth.json
```

Useful flags: `--no-replay` (valid report, no verification), `--corpus-dir` to
point at `kit/corpus_sample`, `--serve --port` to open the screen after writing,
`--no-score` to skip the built-in scorer.

Artifacts, all under the report's directory:

| File | What |
|---|---|
| `loop-report.json` | The deliverable report |
| `golden_set.json` | Frozen golden-set session IDs per finding (written before any prescription) |
| `replay.log` | Every replay call and response |
| `decisions.log` | Append-only record of human approve/reject/defer |

## 4. Pipeline

```
kit/ (logs)
  → io.py         read gzipped JSONL, config_timeline.csv, labels, catalog, manifest
  → features.py   one row per session; step facts folded to session grain under row["derived"]
  → coverage.py   per-tenant emission coverage computed from the corpus
  → detect.py     3 fault detectors (tool contract, KB gap/resolution, efficiency)
  → decoys.py     3 lookalike dismissals (traffic mix, load, judge boundary)
  → asks.py       the 11 operator asks as metrics or gaps
  → standards.py  mine a "good" standard; freeze golden-set IDs
  → diagnose.py / impact.py   cause attribution and impact derivations
  → report.py     assemble + validate loop-report.json
  → replay.py     verify one fix (optional)
  → app.py        decision screen; writes the approval back
```

Run order matters in one place: the detectors run **before** the asks, so the
asks can deconfound themselves against detected faults and decoys.

### Planned advisory layer — not implemented

After the offline loop has produced and validated the report, a future advisory
agent may review that evidence through a constrained harness. The harness would
allow read-only access to `loop-report.json` and tenant-scoped KB retrieval, then
return a cited answer or bounded suggestion to the operator. It would not be
allowed to alter evidence, invent missing metrics, edit the KB, deploy a change,
or record the human verdict.

```text
validated report → advisory harness → report.read + kb.search/kb.read
                                  → cited draft answer / suggestion
                                  → human approve / reject / defer
```

There is no agent runtime or model call in the current solution. The proposed
capabilities, exchange shape, and forbidden actions are defined in
`docs/advisory-agent-harness.md`.

## 5. The data model (the first thing to get right)

The kit has three grains:

- **session** — one whole conversation (resolution, handoff, abandonment, turns, cost);
- **step** — one internal action (tool call, KB lookup, LLM call, guardrail, handoff);
- **turn** — one text exchange.

Steps fan out many-to-one onto sessions. `features.py` builds **one dict per
session** and folds every step fact down to it (`n_tool_calls`, `n_empty_success`
= HTTP 200 / `ok` / an **explicit** `result_field_count == 0`; a missing field is
unknown, not empty; same-tool retries, KB hits and scores, LLM errors, guardrail
blocks, milestones). Every downstream metric works on this session table, so the
fan-out error cannot occur.

---

## 6. Metrics, fidelity and coverage

Every metric is built through one constructor that attaches the "number passport"
at calculation time:

- **value**;
- **fidelity**: `measured` (read from logs), `derived` (computed from other
  numbers), or `judged` (a model/human decided meaning);
- **coverage**: the share of traffic that can even produce the metric, computed
  per tenant from which `agent_kind`s emit the step type;
- **plan**: source, filter, denominator, and the breakdown dimensions actually
  produced;
- **calibration** for judged metrics.

Coverage is measured, not copied: `v2_flow` never emits `tool_call`, so tool
metrics cover ~0.72/0.93; cost, KB and guardrail *are* emitted by v2, so their
coverage is 1.0. Where this contradicts the catalog, the metric carries a
structured `coverage.observed_vs_declared` rather than a vague note.

---

## 7. Fault detection

Three detectors, each owning its own cohort dimensions. A shared window scanner
(`series.py`) finds the contiguous day window whose inside mean differs most from
the outside mean (a Welch z-score), which suits faults that start and end. Window
length is not capped below the corpus length; a 7-day outside requirement is what
bounds it, so a long-running fault can still be enclosed.

1. **Silent tool contract break** — per `(tenant, tool)`: the per-day rate of
   responses that are HTTP 200 / `ok` but carry zero result fields. Requires the
   ordinary tool-error rate to stay flat, resolution to fall, and same-tool
   retries to appear. Attributed to the nearest `kind='tool'` change on that tool.
2. **KB gap / resolution drop** — per `(tenant, intent)`. Mechanism check: KB hit
   rate near zero and low retrieval scores imply `kb.gap`; otherwise `unknown`.
   Baseline is same-tenant, same-window peer intents (never cross-tenant). A
   **born-broken** cohort (new intent, no before-period) opens its window on the
   launch `kind='kb'` change.
3. **Efficiency / prompt regression** — per `(tenant, agent)`: turns and cost
   rise while resolution stays flat. Sibling agents are the peer control, and the
   cause is chosen by the dimension that actually changed in the data
   (`prompt_version` vs `model`), not by the nearest config marker.

**Observation and attribution are separate.** If a mechanism is proven but no
config change aligns, the regression is still reported, with `unknown` cause.

---

## 8. Decoy dismissal

The kit plants three lookalikes; flagging one as a regression costs more than
missing a real problem. Each is emitted as a **non-regression finding with a
linked diagnosis** carrying the exact cause class:

- **traffic_mix** — aggregate moves, one intent's share jumps, per-intent rates
  flat (regression cohorts excused; flatness is a two-proportion z test). Cohorts
  too small for the z-test are checked with an absolute floor and named in
  evidence.
- **load** — volume and latency spike then revert, outcomes flat.
- **judge_change** — quality drops on both tenants at a `judge_version`
  boundary; we never trend quality across it.

---

## 9. Answering the eleven asks

Each ask in `kit/asks.md` becomes a metric or a gap. The four required asks
(A01, A04, A09, A11) are handled as:

- **A01** containment (resolved + by-design handoffs), measured;
- **A04** tool failure rate, measured, with the v3-only coverage stated; plus an
  empty-success metric, derived;
- **A09** a `REQUIRES_NEW_JUDGE` gap (abandonment is measured and reported in the
  gap; the *reason* needs a versioned judge);
- **A11** a `NOT_MEASURABLE` gap with the exact required event (`failover`, step
  grain, `from_target,to_target,reason,recovered`, owner `conversation-runtime`)
  and why the retry proxy misleads.

Among the rest: **A02** reports the raw month-over-month comparison and a
**mix-adjusted** one, with **both ends on the same common-intent scope**, the mix
effect isolated, and any cohort **born in month 2** named; **A03** reports cost
per resolved conversation with escalation beside it, and separates an `unbounded`
intent (zero resolutions) from `cost_unavailable`; **A06** offers the measured KB
hit rate *and* a judged quality reading, segmented by `judge_version` and
calibrated against the kit's human labels — if fewer than 10 labels join it files
a gap rather than going quiet; **A07** compares model upgrades on ±7-day windows
and nulls any comparison a detected event confounds; **A10** is a deterministic
review queue ordered by judged quality within the current judge version.

## 10. Standard, report and verification

- **`standards.py`** mines "what good looks like" from the deployment's own
  resolved, low-turn conversations and **freezes the golden-set session IDs**
  before any prescription exists.
- **`report.py`** assembles findings (with impact, owner, consequence of inaction
  and a derivation), diagnoses (cause class + blamed change), and prescriptions
  (change type, predicted delta, the decision a human approves, the risk, and a
  no-ship condition), then validates against the schema. On a re-run, `run.py`
  carries a recorded `approval` forward onto a prescription with the same
  `(id, diagnosis_id, target)`, so regenerating does not wipe a verdict.
- **`replay.py`** posts the strongest fix to the replay service on the exact
  detected cohort with the frozen golden set, and records run id, before/after,
  verdict and prediction error. `no_effect` is recorded honestly. If the service
  is unreachable the report is still valid with no verifications.

## 11. The decision screen

A single standard-library HTTP server that renders **only** the report:

- `GET /` — the page; `GET /report.json` — the current report (returns `500
  report_invalid` if the file is corrupt rather than dropping the connection);
  `GET /health` — liveness booleans (it does not leak the report path).
- `POST /decision` — `{prescription_id, verdict, decided_by, reason}` (reason
  required). It serializes on a lock, updates exactly that prescription's
  `approval`, re-validates the whole report, writes it through one atomic helper
  (a unique temp file in the target directory, `fsync`, `os.replace`), and appends
  `decisions.log`.

The screen has four tabs — Findings, Refusals, Metrics, Decisions — a grouped left
rail, a finding brief with a coverage chip and harm counters, and a sticky
decision panel. It is intentionally small and complete; it can be restyled as
long as it keeps rendering from the report.

## 12. Results

| Corpus | Result |
|---|---|
| Practice `kit/` | 55.0 / 55 |
| Sealed pool (3 ordinary + 3 hard-mode labels) | 6 / 6 pass, all 55.0 |
| Moved-fault (faults relocated across tenants/slices) | 55.0 |
| Moved-fault + a clean unseen third tenant | 55.0 |

All faults are found with the right cohort and cause; all three lookalikes are
explicitly dismissed; no false alarms, strays, honesty gaps, hardcoded labels,
non-determinism or replay-provenance problems.

## 13. Demo script (about ten minutes)

1. **The problem** (1 min): a deployed agent, logs, and a configuration timeline;
   the operator needs one decision, not a dashboard.
2. **Coverage first** (1 min): show the coverage chip. The tool metric covers
   ~0.72/0.93 because `v2_flow` emits no tool calls; state the declared-vs-observed
   disagreement.
3. **The silent failure** (3 min): open findings; the first finding is the empty
   HTTP 200. Point at the flat error metric and the same-tool retries — this is
   the failure alerting cannot see.
4. **The lookalikes** (2 min): open the dismissed signals; mix, load and the judge
   boundary, each with a written reason.
5. **Refusals** (1 min): A11 leads the refusals tab — the required event is named
   and the retry proxy is rejected.
6. **Decide** (1 min): record an approve/reject with a reason; show it written
   back into `loop-report.json`.
7. **Verification** (1 min): show the replay block — run id, before/after,
   prediction error — and note that the replay service is a verifier, not a search.

## 14. What is real, stubbed, and where it breaks

In short: all facts come from logs and deterministic Python; no LLM is called;
A09 is a gap rather than a judge; quality calibration is the kit's human labels
against the corpus judge; the replay service is a seeded hypothesis verifier;
everything is in-memory (fine at ~80k sessions, not at 10–100×). The full note is
`docs/submission-note.md`.
